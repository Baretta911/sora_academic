**SORA Academic** = Sleep Optimization and Rest Arrangement menggunakan Genetic Algorithm

- **Tujuan**: Optimasi jadwal harian akademis dengan pertimbangan tidur, kerja, nap, istirahat, dan kelas
- **Algoritma Core**: Genetic Algorithm + Hill Climbing local search

- **Technology**: NumPy, Streamlit, Pytest
- **Status**: THESIS PROJECT (setiap keputusan harus well-documented)

## Problem Domain

### Schedule Representation

```
1 individual = 1 daily chromosome
1 chromosome = 48 genes (time slots)
1 gene = 30-minute time slot (14 time per day)

Allele values:
  0 = main sleep
  1 = work
  2 = nap
  3 = rest
  4 = class
```

### Key Parameters (from config.py)

```python
GENES_PER_DAY = 48
SLOT_DURATION_HOURS = 0.5  # 30 minutes

# GA defaults
DEFAULT_POPULATION_SIZE = 50
DEFAULT_MUTATION_RATE = 0.10
DEFAULT_CROSSOVER_RATE = 0.80

# Sleep targets (in slots, so 1 slot = 30 min)
BASE_SLEEP_TARGET_SLOTS = 14  # 7 hours
MIN_SLEEP_SLOTS = 12  # 6 hours
MAX_SLEEP_SLOTS = 18  # 9 hours

# Penalty weights
PENALTY_WEIGHTS = {
    "BLOCK": 300.0,      # Too many sleep blocks
    "DURATION": 200.0,   # Sleep too short/long
    "NAP_EARLY": 150.0,  # Nap outside recommended window
    "NAP_OVER": 150.0,   # Too much napping
    "REGULARITY": 100.0, # Inconsistent schedule
}
```

### Fitness Function

```
fitness = 0.65 * (recovery_reward + actual_duration * 0.2)
        + dynamic_penalty
        + regularity_penalty

Higher = Better. Negative values valid (penalties exceed rewards).
```

## Coding Standards

### Genetic Algorithm Rules

1. **Crossover**: Single-point at random slot [10, 37]
2. **Mutation**: Only non-mandatory genes; nap window (24-33) has special probabilities
3. **Elitism**: Copy top 20 individuals (if population > 20) to next generation
4. **Repair**: Ensure constraints satisfied after genetic operations

### Code Style

- Type hints required for function signatures
- Docstrings for modules, classes, and public methods
- Use NumPy for array operations (not lists)
- Chromosome representation: numpy arrays of shape (48,)
- Population representation: numpy arrays of shape (population_size, 48)

### Testing

- Write tests in `tests/` using Pytest
- Test naming: `test_<module>_<function>`
- Minimum coverage: 80% for core GA modules
- Run: `.\.venv\Scripts\pytest.exe -q`

## When Explaining Code

- **Always reference the slot/gene/allele framework**: clarify what each chromosome represents
- **Mention fitness tradeoffs**: penalties vs. recovery rewards
- **Explain GA operators in context**: how crossover preserves structure, why mutation respects nap window
- **Use concrete examples**: "slot 24-33 is the nap window (2 hours)", "fitness can be negative"

## When Implementing Features

1. **Understand the constraint**: which alleles are valid where?
2. **Consider fitness impact**: does it help or hurt the optimization?
3. **Check crossover/mutation safety**: won't break chromosome validity
4. **Add tests first** (TDD): write test before implementation
5. **Verify with experiments**: run baseline or calibration to validate

## Key Decision Points

- **Individual representation**: Always 1D array of 48 slots? Or nested structure?
  → Use 1D numpy array (48,) for efficiency
- **Constraint repair**: Repair after genetic op or prevent violations?
  → Repair after, then re-evaluate fitness
- **Population diversity**: How to maintain without premature convergence?
  → Adjust mutation_rate (default 0.10) and crossover_rate (default 0.80)
- **Sleep quality tradeoffs**: Short sleep vs. irregular schedule?
  → Fitness function weights: duration (200.0) > regularity (100.0)

## Debugging Hints

- **Fitness all negative**: Check penalty weights—may be too harsh
- **No convergence**: Mutation rate too high? Increase elite_count?
- **Validation errors**: Likely constraint violation—check repair.py logic
- **Streamlit UI hangs**: Check experiment runner—may be blocking on long GA run

## ❌ DON'Ts (JANGAN LAKUKAN)

### Algorithm Mistakes
- **DON'T** hardcode parameters di code
  → Put di config.py dengan alasan di dokumentasi
- **DON'T** modify chromosome tanpa repair
  ```python
  ❌ chromosome[10:20] = 1  # Might violate constraints!
  ✅ chromosome[10:20] = 1; repair(chromosome); fitness(chromosome)
  ```
- **DON'T** forget elitism
  → Best solutions hilang ke generasi berikutnya = konvergensi jelek
- **DON'T** use mutation_rate terlalu tinggi
  → Akan destroy good solutions, tidak konvergen
  → Default 0.10 (10%) itu tested dan OK
- **DON'T** crossover di slot 0-9 atau 38-47
  → Reserved untuk constraints, gunakan slot [10,37]

### Code Quality Mistakes
- **DON'T** print debugging ke output production
  ```python
  ❌ print(f"Fitness: {fit}")  # Akan pollute Streamlit UI
  ✅ logger.debug(f"Fitness: {fit}")  # Silent dalam production
  ```
- **DON'T** ignore type checking
  ```python
  ❌ def optimize(pop):  # Type? Size? Range?
  ✅ def optimize(pop: np.ndarray) -> np.ndarray:  # Clear!
  ```
- **DON'T** skip tests
  → Sekali break, thesis methodology jadi questionable
- **DON'T** magic numbers di code

### Research Mistakes

## 🎯 COMMON ACADEMIC PITFALLS & Solutions

### Pitfall 1: "I ran GA, got a schedule, but why is it good?"
**Problem**: No baseline comparison, can't claim improvement
**Solution**: 
- Generate random schedules (100x)
- Generate greedy schedules (slot-by-slot priority)
- Compare GA fitness vs random/greedy with confidence intervals
- Show: GA = X%, Random = Y%, Greedy = Z% (statistically significant?)

### Pitfall 2: "GA works for subject A but fails for subject B"
**Problem**: Algorithm not generalizable, thesis weak
**Solution**:
- Identify why it fails (which constraints problematic?)
- Adjust penalty weights or GA parameters for that profile
- Document: "GA parameter tuning needed per subject profile"
- Propose adaptive tuning as future work

### Pitfall 3: "Fitness is negative, so GA is bad?"
**Problem**: Misunderstanding fitness function design
**Solution**:
- Negative fitness is VALID if constraints are hard
- It means "penalties exceed recovery rewards"
- Check: Are all constraints satisfiable?
- If not: Adjust constraints, not penalty weights (wrong direction!)

### Pitfall 4: "I changed parameter X and got better results"
**Problem**: Undocumented experiment, not reproducible
**Solution**:
- Log EVERY parameter change with date + reason
- Keep version history (git commit)
- Show before/after results
- Explain: Why did this change help? (hypothesis confirmation)

### Pitfall 5: "UI looks cool but crashes under load"
**Problem**: Production readiness ignored
**Solution**:
- Test Streamlit with large datasets
- Add error handling + user feedback
- Show loading spinner for long GA runs
- Log all errors for debugging
